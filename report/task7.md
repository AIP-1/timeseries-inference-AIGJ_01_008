# 과제 7. 엣지 최적화

## 해결한 것

1. **학습한 모델 5개(예측 GRU·LSTM·TCN, 이상 탐지 오토인코더, 환기 경보 MLP)를 TensorRT FP16으로 변환**했다. GRU·LSTM은 FP16에서 차이가 기준을 조금 넘어, 순환층만 FP32로 두는 혼합 정밀도로 다시 변환했다.
2. **네 가지 실행 방식(PyTorch CPU, PyTorch GPU, ONNX Runtime, TensorRT)의 지연**을 평균과 느린 쪽 5%(p95)로 쟀다. 배치 1(한 공간)과 배치 4(네 공간)를 모두 재고, 배치 4도 거의 같았다(아래 표는 배치 1).
3. **변환 전후 결과 차이를 원래 단위로** 쟀다. CO₂ 예측은 최대 몇 ppm 달라졌는지, 분류는 판정이 바뀐 비율로 봤다.
4. **측정 중 전력과 메모리**를 기록했다. 보드 전체 전력은 7.2~9.1W였다. TensorRT 최대 배치를 4,096에서 64로 줄이자 실행 메모리가 215MB에서 수 MB로 줄었다.

**지연 (ms, 평균 / p95, 배치 1)과 변환 차이**

| 모델 | PyTorch CPU | PyTorch GPU | ONNX Runtime CPU | TensorRT FP16 | FP16 변환 후 최대 차이 |
|---|---|---|---|---|---|
| 예측 GRU 4시간 | 32.1 / 36.1 | 1.18 / 1.30 | **0.34 / 0.35** | 1.70 / 1.73 | CO₂ 1.10ppm (평균 0.06) |
| 예측 LSTM 4시간 | 4.42 / 4.41 | 1.16 / 1.21 | **0.42 / 0.45** | 1.66 / 1.71 | CO₂ 1.03ppm |
| 예측 TCN 4시간 | 2.68 / 3.11 | 3.07 / 3.22 | **0.23 / 0.25** | 0.58 / 0.64 | CO₂ 0.25ppm |
| 이상 탐지 오토인코더 | 1.10 / 1.60 | 1.09 / 1.26 | **0.04 / 0.04** | 0.40 / 0.42 | 재구성 0.001 |
| 환기 경보 MLP | 2.61 / 3.59 | 0.80 / 0.90 | **0.03 / 0.04** | 0.32 / 0.34 | 판정 바뀜 0% |

**혼합 정밀도로 다시 변환한 결과**

| 모델 | 정밀도 | CO₂ 최대 차이 (ppm) | 배치 1 평균 / p95 (ms) | 엔진 (KB) |
|---|---|---|---|---|
| GRU | FP16 전체 | 0.94~1.10 (빌드마다 다름) | 1.70 / 1.81 | 537 |
| GRU | **혼합(순환층 FP32)** | **0.27** | 1.74 / 1.82 | 701 |
| LSTM | FP16 전체 | 1.01~1.03 | 1.67 / 1.83 | 556 |
| LSTM | **혼합(순환층 FP32)** | **0.27** | 1.74 / 1.81 | 749 |

*측정 조건: 보드 25W 모드, 클럭 고정 안 함, 워밍업 50회 뒤 500회 측정. 입력은 합성 시험 기간. TensorRT 수치에는 매 호출의 CPU↔GPU 복사가 들어 있다. 모델마다 새 프로세스로 쟀다.*

## 확인 기준

| 기준 | 결과 | 판정 |
|---|---|---|
| 변환 후 CO₂ 예측 차이 1ppm 이하 | TCN 0.25ppm. GRU·LSTM은 FP16 전체에서 1.03~1.10ppm으로 조금 넘었고, 혼합 정밀도로 0.27ppm | 통과 (혼합 정밀도 포함) |
| 분류 결과가 바뀐 비율 0.1% 이하 | 환기 경보 0% | 통과 |
| 측정 조건(전력 모드, 클럭 고정, 반복, 워밍업) 기록 | 위 측정 조건 | 통과 |

## 산출물

- **최적화 보고서**: 위 두 표. 결론은 **지금 서비스 규모(공간 3~4개, 1분 주기)라면 ONNX Runtime CPU가 가장 좋다**는 것이다. GPU는 로컬 LLM에 남겨 둔다.

## 생각해 볼 점

- **CPU로 1ms면 충분한데 왜 변환하나**: 이 크기 모델은 실제로 ONNX Runtime CPU가 가장 빨랐다(0.03~0.42ms). 그래도 변환이 의미 있는 경우는 세 가지다. 로컬 LLM이 CPU를 쓰는 동안 시계열을 GPU로 빼낼 때, 공간이 수십 개로 늘어 한 번에 처리할 양이 커질 때, 같은 일을 더 적은 전력으로 할 때다.
- **순환망(GRU·LSTM)과 합성곱(TCN) 중 무엇이 더 빨라지나**: TCN만 빨라졌다(PyTorch GPU 3.07 → TensorRT 0.58ms). GRU·LSTM은 오히려 느려졌다(1.2 → 1.7ms). 합성곱은 한 번에 병렬로 계산되지만, 순환망은 48칸을 하나씩 차례로 계산해야 해서 GPU의 이득이 작다. 같은 이유로 순환망은 반정밀도 반올림 오차가 48칸을 지나며 쌓여 차이가 커졌다.
- **평균보다 느린 쪽 5%가 중요한 이유**: 상시 서비스는 매분 정해진 시각에 결과를 내야 한다. 평균이 빨라도 가끔 수백 ms씩 튀면 그 주기의 결과가 늦거나 다른 작업과 겹친다. PyTorch CPU GRU는 배치 4에서 평균 36ms에 p95 68ms로 흔들림이 가장 컸다.

## 심화(B)

- **INT8 변환**: 예측 TCN·GRU·LSTM과 이상 탐지 오토인코더를 INT8로 변환했다(학습 기간 입력 1,024개로 보정). 정확도 손실은 사실상 없었다. 60분 CO₂ 오차 차이가 0.002ppm 이하이고, 이상 판정이 바뀐 비율은 0%다. 대신 속도 이득도 없었다. 모델이 아주 작아(1회 0.3~1.8ms) 계산보다 실행 준비와 메모리 복사가 대부분이고, GRU·LSTM의 순환층은 INT8로 바뀌지 않고 FP16으로 남았기 때문이다. 이 크기의 모델은 INT8을 쓸 이유가 없고(빌드만 TCN 213초), INT8은 Chronos처럼 큰 모델에 시도할 가치가 있다.
- **모델 4개를 동시에 올렸을 때의 메모리와 로컬 LLM 조합**: 예측 GRU·오토인코더·사용 여부·환기 경보를 한 프로세스에 올려 세 방식으로 재어 보았다(아래 표). 모델 자체는 100MB 안팎이고, 메모리의 대부분은 PyTorch·TensorRT 같은 라이브러리가 쓴다. **네 모델은 ONNX Runtime CPU로 돌리고, GPU와 남는 메모리는 LLM에 맡기는 조합**을 제안한다. 이때 가용 메모리는 약 2.9~3.2GB로, 4비트 양자화 1~2B 모델(약 1.5GB)은 들어가고 1GB 이상 남는다. 3B 4비트(약 2GB 이상)는 여유가 0.5GB 아래로 떨어져 위험하다. 이 보드는 스왑이 없어 메모리가 모자라면 멈추므로, 가용 1GB 이상을 항상 남기는 것을 조건으로 둔다.

**INT8 변환 결과** (60분 CO₂ 오차와 1회 추론 시간, 배치 1 평균)

| 모델 | FP32 | FP16 | INT8 | FP32 대비 최대 차이 (INT8) |
|---|---|---|---|---|
| TCN | 20.98ppm · 0.47ms | 20.98ppm · 0.46ms | 20.98ppm · 0.47ms | CO₂ 0.39ppm |
| GRU | 21.28ppm · 1.68ms | 21.28ppm · 1.78ms | 21.28ppm · 1.81ms | CO₂ 1.45ppm |
| LSTM | 22.85ppm · 1.67ms | 22.84ppm · 1.71ms | 22.84ppm · 1.72ms | CO₂ 1.01ppm |
| 오토인코더 | 0.31ms | 0.30ms | 0.33ms | 이상 판정 바뀜 0% |

*측정 조건: 합성 데이터 시험 기간 전체 샘플(예측 6,201개, 오토인코더 창 8,064개). 여기 오차는 전체 샘플 기준이라 과제 3 표(평가 지점 기준)와 조금 다르다. 보드 25W, 클럭 고정 안 함, 워밍업 50회·500회 측정, 엔진마다 새 프로세스.*
