## 6-1. 공변량(온습도·일정)을 받는 사전학습 모델

**한 일**
- Chronos-Bolt는 CO₂ 한 줄만 받아서, 공변량을 받는 **Chronos-2**(amazon/chronos-2, 1.2억 개 파라미터, chronos-forecasting 2.3.2)를 썼습니다. 이미 깔린 패키지에 들어 있었고, 학습 없이(zero-shot) GPU에서 돌렸습니다.
- 입력은 세 가지로 비교했습니다.
  - A. CO₂만
  - B. CO₂ + 과거 온도·습도
  - C. B + 예정 인원(sched_people)·시각(sin/cos). 이 셋은 앞으로 60분 값도 미리 알려 줍니다.
- 과거 길이(24시간, 1주)는 검증 60분 MAE로 골랐는데, 세 가지 모두 1주가 골라졌습니다.

**결과: 시험 기간 CO₂ MAE(ppm), 시험 지점 약 6,000개**

| 입력 | 5분 | 15분 | 30분 | 60분 | 검증 60분 |
|---|---|---|---|---|---|
| A. CO₂만 | 6.74 | 9.86 | 14.48 | 21.35 | 27.29 |
| B. + 온도·습도 | 6.79 | 9.96 | 14.19 | 20.97 | 27.79 |
| C. + 온도·습도 + 일정·시각 | 6.73 | 9.89 | 13.51 | **17.62** | 23.66 |
| (참고) GRU 4시간, 직접 학습 | 7.26 | 10.49 | 14.03 | 20.52 | 21.12 |
| (참고) Chronos-Bolt-base 1주 | 8.48 | 12.11 | 17.21 | 27.85 | 35.48 |

| 항목 | 값 |
|---|---|
| 1회 추론, 배치 1, 과거 24시간 | A 87.9ms / B 91.8ms / C 92.2ms (p95 89.9 / 92.4 / 94.6ms) |
| GPU 메모리(모델 / 최대) | 456MB / 642MB |
| 평가 시간(검증 24시간·1주 + 시험 1주) | A 약 9분, B 약 27분, C 약 53분 |

**측정 조건**: GPU, FP32, 계열 묶음 32, 지점 묶음 64. 10~90% 구간 적중률은 0.72~0.76입니다(`report/b6_covariates_results.csv`).

**해석**
- 온습도만 더하면 거의 그대로였습니다(60분 21.35 → 20.97). 앞으로의 **예정 인원과 시각**을 함께 주자 60분 오차가 17.6ppm으로 줄어, 직접 학습한 GRU(20.5)보다 좋아졌습니다. CO₂ 변화는 사람 수가 정하므로, 미래에 알 수 있는 일정 정보가 가장 큰 도움이 됩니다.
- 대신 1회 추론이 약 90ms로 GRU(1~2ms)보다 수십 배 느리고, GPU 메모리도 약 0.6GB를 씁니다. 5분 주기 서비스에는 충분히 빠르지만 메모리가 빠듯한 이 보드에서는 상시로 올려 두기 부담스럽습니다. 우선 정확도 비교 기준으로 쓰고, 상시 서비스는 GRU를 유지하는 것이 낫습니다.

## 6-2. 직접 학습한 모델 + 사전학습 모델 섞기

**한 일**
- GRU(과거 4시간, `models/forecast_gru_L48.pt`)와 Chronos-Bolt small/base(과거 1주)의 예측을 같은 지점에서 섞었습니다.
- GRU의 검증·시험 예측은 저장된 모델로 다시 만들었습니다. 시험 60분 MAE는 20.52로 기존 기록과 같습니다.
- Bolt의 검증 예측은 새로 만들었습니다(`b6_bolt_val.py`).
- 섞는 방법은 세 가지입니다.
  1. 단순 평균(0.5:0.5)
  2. 검증 60분 MAE가 가장 작은 GRU 비중 w(0~1, 0.05 간격) 하나
  3. 예측 거리마다 따로 고른 w
- 두 모델의 예측이 모두 있는 지점만 썼습니다(시험 60분 기준 6,045개).

**결과: 시험 기간 CO₂ MAE(ppm)**

| 조합 / 방법 | 5분 | 15분 | 30분 | 60분 |
|---|---|---|---|---|
| GRU 단독 | 7.26 | 10.49 | 14.03 | 20.52 |
| Bolt-small 단독 | 9.44 | 13.74 | 19.75 | 30.40 |
| GRU+small 단순 평균 | 7.56 | 10.84 | 14.96 | 23.03 |
| GRU+small 검증 비중(GRU 0.95) | 7.16 | 10.33 | 13.82 | 20.35 |
| GRU+small 거리별 비중(0.85~0.95) | 7.07 | 10.23 | 13.69 | 20.35 |
| Bolt-base 단독 | 8.48 | 12.11 | 17.21 | 27.85 |
| GRU+base 단순 평균 | 7.18 | 10.18 | 13.90 | 21.85 |
| GRU+base 검증 비중(GRU 0.95) | 7.14 | 10.32 | 13.80 | 20.28 |
| GRU+base 거리별 비중(0.80~0.95) | **6.98** | **10.09** | **13.64** | **20.28** |

검증으로 고른 GRU 비중: 5분 0.80~0.85, 15분 0.85~0.90, 30분 0.90, 60분 0.95(`report/b6_ensemble_weights.csv`).

**해석**
- 단순 평균은 짧은 거리(5·15분, base와 섞을 때)에서만 조금 나았고, 60분에서는 오히려 나빠졌습니다(20.5 → 21.9~23.0). Chronos-Bolt가 GRU보다 훨씬 부정확해서, 반반 섞으면 나쁜 쪽에 끌려갑니다.
- 검증으로 비중을 고르면 GRU 비중이 0.8~0.95가 되고, 두 모델 모두보다 조금 나아졌습니다(5분 7.26 → 6.98, 60분 20.52 → 20.28). 다만 차이가 0.2~0.3ppm으로 작습니다. 모델을 하나 더 돌리는 비용(1주 과거, GPU)에 비하면 이득이 거의 없습니다.
- 주의할 점: GRU는 검증 기간으로 학습 종료 시점을 골랐기 때문에 검증 오차가 조금 낙관적입니다. 그래서 비중이 GRU 쪽으로 기울었을 수 있습니다.
- 섞기를 한다면 Bolt보다 6-1의 Chronos-2 C(60분 17.6)와 섞는 쪽이 더 유망합니다. 이번에는 해 보지 않았습니다.

## 7-3. TensorRT INT8 변환

**한 일**
- 예측 TCN·GRU·LSTM(과거 4시간)과 이상 탐지 AE를 TensorRT로 변환했습니다. 같은 ONNX(`models/<모델>.onnx`)에서 FP32·FP16·INT8 엔진을 만들었습니다.
- INT8 보정은 학습 기간 입력 1,024개(무작위, seed 0)로 했습니다. 방식은 엔트로피 보정(IInt8EntropyCalibrator2), 보정 묶음은 32입니다. INT8로 돌 수 없는 층은 TensorRT가 FP16으로 남깁니다.
- 정확도 기준은 PyTorch CPU FP32 출력입니다.
  - 예측 모델: 시험 기간 샘플 6,201개 전체
  - AE: 시험 기간 창 8,064개, 임계값 0.38(기준 판정으로 이상이 213개)

- run_optimize.sh와 같게 했습니다: 워밍업 50회 + 측정 500회, 배치 1과 4, 엔진 하나당 프로세스 하나, 작업 공간 64MB.
- 결과 파일: `report/b7_int8_latency.csv`, `b7_int8_accuracy.csv`, `b7_int8_meta.json`.
- 과제 7 표(optimize_latency.csv)는 PyTorch로 버퍼를 다뤘고, 이번에는 cuda-python으로 다뤘습니다. 그래서 같은 FP16이라도 수치가 조금 다릅니다(TCN 0.58 → 0.46ms). 이 표 안의 FP32·FP16·INT8 비교는 같은 조건입니다.

**해석**
- **정확도 손실은 사실상 없습니다.** 60분 MAE 차이가 0.002ppm 이하이고, AE 이상 판정도 하나도 바뀌지 않았습니다.
- **속도 이득도 없습니다.** INT8이 FP16·FP32보다 빠르지 않았습니다.
  - GRU·LSTM의 INT8 출력이 FP16과 똑같은 것으로 보아, 순환층은 INT8로 바뀌지 않고 FP16으로 남은 것으로 보입니다.
  - TCN·AE는 모델이 아주 작아서(1회 0.3~0.5ms) 계산보다 실행 준비와 메모리 복사 시간이 대부분을 차지합니다. 그래서 정밀도를 낮춰도 줄어들 계산이 거의 없습니다.
- 이 모델들은 INT8을 쓸 이유가 없습니다. 빌드만 오래 걸립니다(TCN 213초). FP16이나 ONNX Runtime CPU(과제 7: 0.03~0.4ms)를 쓰는 것이 낫습니다. INT8은 Chronos처럼 큰 모델에 시도할 가치가 있습니다.

## 7-4. 모델 4개를 함께 올렸을 때 메모리, LLM과 같이 올릴 조합

**한 일**
- 한 프로세스에 예측 GRU + 이상 탐지 AE + 재실 판정(occ.pkl, sklearn) + 환기 경보를 올리고, 세 가지 방식으로 비교했습니다(방식마다 새 프로세스).
  - PyTorch CPU: 지금 서비스 방식. 환기 경보는 vent.pkl
  - ONNX Runtime CPU: 환기 경보는 vent.pkl
  - TensorRT FP16: 환기 경보는 MLP 엔진. torch 없이 cuda-python 사용
- 재실 판정은 결정트리 앙상블이라 GPU로 바꿀 수 없어서, 세 방식 모두 CPU로 두었습니다.
- 각 단계(라이브러리 import, 모델 적재, 추론 20회 뒤)마다 프로세스 RSS와 보드 가용 메모리(`free`의 available)를 쟀습니다.

**결과**

| 방식 | 라이브러리만(RSS) | 4개 적재+추론 뒤 RSS | 보드 가용 메모리 감소 | 4개 한 바퀴(배치 4) |
|---|---|---|---|---|
| PyTorch CPU | 548MB | 658MB | 330MB | 54.2ms |
| **ONNX Runtime CPU** | 166MB | **176MB** | **111MB** | 60.8ms |
| TensorRT FP16 | 582MB | 762MB | 286MB | 17.2ms |

- 모델 자체가 차지하는 메모리는 모두 100MB 안팎입니다. 메모리의 대부분은 라이브러리(PyTorch·TensorRT·CUDA)가 씁니다.
- 한 바퀴 시간은 CPU 방식에서 대부분 sklearn 환기 모델(vent.pkl) 몫입니다. TensorRT 방식은 MLP로 바꿔서 빠릅니다.
- 측정할 때 보드: 전체 7,485MB. 내 서비스(PyTorch, RSS 약 700MB), 팀원 서비스·InfluxDB 2개·VS Code 서버·데스크톱이 떠 있는 상태에서 **가용 메모리 약 2.7GB**(17:38 측정)였습니다.

**제안: LLM과 같이 올릴 조합**
- **4개 모델은 ONNX Runtime CPU로 돌리고, GPU와 남는 메모리는 LLM에 맡기는 조합**이 가장 여유가 많습니다.
  - 지금 서비스(PyTorch CPU, 약 330MB)를 ONNX Runtime(약 110MB)으로 바꾸면 RSS 기준 약 0.2~0.5GB를 더 확보합니다. 그러면 가용 메모리가 약 2.9~3.2GB가 됩니다.
  - TensorRT 방식은 추론이 빠르지만, 같은 보드에서 LLM도 CUDA를 쓰면 CUDA 런타임을 두 프로세스가 따로 올리게 됩니다. 이번 INT8 빌드 때도 엔진 하나에 가용 메모리가 1.1~1.3GB 줄었습니다.
- 크기 기준: 4비트 양자화 1~2B 모델(가중치 약 1~1.3GB, 짧은 문맥 KV 캐시 포함 1.5GB 안팎)은 들어가고, 1GB 이상 여유가 남습니다. 3B 4비트(약 2GB 이상)는 여유가 0.5GB 아래로 떨어져 위험합니다.
- 오늘 Chronos-Bolt-base를 묶음 128로 돌리다가 보드가 멈춘 것처럼, 이 보드는 스왑이 없어서 메모리가 모자라면 멈춥니다. 그래서 **가용 메모리 1GB 이상을 항상 남기는 것**을 조건으로 둡니다.
- 결과 파일: `report/b7_memory_torch.json`, `b7_memory_ort.json`, `b7_memory_trt.json`.

## 공통 측정 조건과 오늘 있었던 일

- 전원 25W(nvpmodel), 클럭 고정 안 함. GPU 작업은 한 번에 하나만 실행기 `b_gpu_run.sh`로 돌렸습니다. 실행기는 시작 전에 가용 메모리를 확인하고, 내 계정의 다른 python 작업이 없는지 확인하고, 잠금 파일을 잡습니다. 실행 중에는 가용 메모리를 10초마다 로그에 남깁니다.
- **보드 정지(15:27)**
  - Chronos-Bolt 검증 예측을 묶음 128로 돌리던 중이었습니다. small은 끝났고, base 차례에서 GPU 메모리 할당이 실패했습니다(`NvMapMemHandleAlloc failed: error 12`). 이어서 PyTorch CUDA 오류가 났고, 보드가 응답하지 않아 전원을 껐다 켰습니다(15:34 부팅).
  - 시작할 때 가용 메모리는 2.45GB였고, small 실행 중 0.93GB까지 떨어졌습니다. 기록은 `report/b6_bolt_val_run_crash_1525.log`에 있습니다.
- **바꾼 설정**
  - Bolt 묶음 128 → 16, 모델별로 프로세스를 나눔
  - Chronos-2 묶음은 계열 32, 지점 64
  - 시작 조건을 가용 1.5GB → 2.5GB로 올림. 단 작은 모델만 다루는 7-3·7-4는 2.0GB. 재부팅 뒤 평상시 가용량이 약 2.3~2.8GB라 2.5GB를 넘지 못하는 때가 있었습니다.
- **INT8 첫 시도(17:19)**
  - 한 프로세스에서 PyTorch CUDA를 쓰면서 엔진 3개를 연달아 만들자 가용 메모리가 647MB까지 떨어져 바로 중단했습니다. 기록은 `report/b7_int8_fc_tcn_aborted_1719.log`에 있습니다.
  - 다시 할 때는 입력을 CPU 단계에서 미리 만들고, GPU 단계는 TensorRT + cuda-python만 쓰고, 엔진 하나당 프로세스 하나, 작업 공간 64MB로 바꿨습니다. 그 뒤 가용 메모리는 가장 낮을 때 1.39GB였습니다.
- **각 작업 중 가장 낮았던 가용 메모리**: Bolt base 재실행 약 1.8GB, Chronos-2 1.23GB, INT8 1.39GB, 4개 동시 적재 2.35GB.
- 재부팅 뒤 내 서비스는 자동으로 다시 떴습니다(:8090/health 정상, 15:37에 InfluxDB(:8087) 읽기 시간 초과 1번).
