# 실행 방법

보고서의 모든 숫자는 팀 Jetson의 team2-2 계정에서 이 저장소의 코드를 아래 명령으로 돌려 얻었다. 제공 키트나 팀원 코드는 쓰지 않았다.

보드에서는 `src/`가 `~/work/ts`, `sim/`이 `~/work/sim`, `collector/`가 `~/ingest`에 있다. 아래 명령은 `~/work/ts`에서 실행한다. 파이썬은 `requirements.txt`의 패키지를 설치한 가상환경 `~/venv/bin/python`을 쓴다(TensorRT는 JetPack에 맞는 판을 쓴다). GPU로 돌릴 때는 명령 앞에 `DEV=cuda`를 붙인다.

## 한눈에 보기

| 과제 | 코드 | 결과 파일 (`results/synthetic/`) |
|---|---|---|
| 합성 데이터 | `sim/generate.py` | 센서값, 일정, 정답, 고장 목록(저장소에는 넣지 않음. seed 42로 같은 값이 나온다) |
| 1 수집 | `collector/` (Docker) | `results/collector/coverage_날짜.md` |
| 2 진단·기준선 | `diagnose.py`, `baselines.py` (전처리는 `prep.py`) | `diag_*.csv`, `baseline_*.csv`, `eval_points.csv.gz`, 그래프 |
| 3 60분 예측 | `train_forecast.py` | `forecast_results.csv` |
| 4 이상 탐지 | `anomaly.py` | `anomaly_scorecard.csv` |
| 5 상태 추정 | `state.py` | `state_occupancy.csv`, `state_vent.csv` |
| 6 사전학습 모델 | `pretrained.py` (`run_pretrained.sh`로 실행) | `pretrained_results.csv` |
| 7 엣지 최적화 | `optimize.py` (`run_optimize.sh`로 실행), `trt_mixed.py` | `optimize_*.csv` |
| 8 상시 서비스 | `service.py` (`run_service.sh`로 실행) | `results/service/` |

## 명령

**합성 데이터 만들기**

```bash
~/venv/bin/python ~/work/sim/generate.py --out ~/work/data/synthetic --weeks 6 --seed 42
```

**과제 1: 수집기**

`collector/.env.example`을 `.env`로 복사해 값을 채운 뒤 실행한다.

```bash
cd ~/ingest && docker compose up -d
```

**과제 2: 진단과 기준선**

```bash
~/venv/bin/python diagnose.py
```

```bash
~/venv/bin/python baselines.py
```

**과제 3: 60분 예측 (GPU)**

모델 3종 × 과거 길이 3종, 일정 제외, 처음 보는 공간 실험까지 한 번에 돈다. 하나만 돌릴 때는 `train_forecast.py gru 48`처럼 쓴다.

```bash
DEV=cuda ~/venv/bin/python train_forecast.py
```

**과제 4·5: 이상 탐지, 상태 추정**

```bash
~/venv/bin/python anomaly.py
```

```bash
~/venv/bin/python state.py
```

**과제 6: 사전학습 모델 (GPU, 모델 3개를 차례로)**

```bash
./run_pretrained.sh
```

**과제 7: 엣지 최적화 (모델마다 새 프로세스)**

```bash
./run_optimize.sh
```

```bash
~/venv/bin/python trt_mixed.py
```

**과제 8: 상시 서비스**

서비스가 죽으면 이 스크립트가 10초 뒤 다시 띄운다.

```bash
./run_service.sh
```

자동으로 도는 일은 cron에 등록돼 있다.

| 언제 | 하는 일 |
|---|---|
| 재부팅할 때 | 추론 서비스 시작(`run_service.sh`) |
| 매일 09:05 | 수집 현황 보고서 만들기 |
| 매시간 17분 | PostgreSQL에 빠진 값 채우기 |

**실데이터로 다시 돌릴 때**

같은 코드를 `~/work/ts_real` 폴더에서 데이터 위치만 바꿔 돌렸다.

```bash
cd ~/work/ts_real && DEV=cuda TS_DATA=$HOME/work/data/real ~/venv/bin/python train_forecast.py
```

## 파일 설명

**데이터 만들기·모으기**

| 파일 | 하는 일 | 들어가는 것 → 나오는 것 |
|---|---|---|
| `sim/generate.py` | 가짜 교육장 데이터를 만든다. 시간표·예약을 만들고, 실제 인원은 결석·노쇼·연장으로 일부러 어긋나게 한다. 사람 수에 따라 CO₂·온도가 오르내리는 물리 계산을 1분마다 하고, 빠진 값·깨진 값·흔들림을 넣는다. 마지막 1주에는 고장 5종 17건을 심는다 | 설정(기간 6주, 시드 42) → 센서값, 일정, 정답, 고장 목록 |
| `collector/collector/collector.py` | MQTT 메시지를 받아 InfluxDB와 PostgreSQL에 저장한다. 메시지를 어떻게 읽을지는 `config.yaml`에서 정한다. 끊기면 다시 붙고, 못 쓴 값은 보관했다가 다시 쓴다. 같은 메시지가 두 번 오면 거른다 | MQTT 메시지 → 저장된 센서값, 1분마다 수집기 상태 |
| `collector/collector/report.py` | 수집 현황 보고서를 만든다. 센서별 커버율을 계산하고, 빈 구간의 원인을 센서 일련번호(fCnt)와 수집기 기록으로 나눈다 | 저장된 값 → 보고서(매일 09:05) |
| `collector/collector/backfill.py` | PostgreSQL에 빠진 구간을 InfluxDB에서 다시 채운다. 시계가 빨랐던 게이트웨이의 시각도 고쳐서 넣는다 | InfluxDB → PostgreSQL(매시간) |

**공통 부품 (여러 과제가 같이 씀)**

| 파일 | 하는 일 |
|---|---|
| `src/prep.py` | 전처리. 나올 수 없는 값을 빈칸으로 바꾸고, 5분씩 묶어 평균을 내고, 15분 이하 빈칸을 메우고, 학습·검증·시험 기간을 나누고, 정규화 값을 학습 기간으로만 계산한다. 학습과 서비스가 이 파일 하나만 써서 전처리가 어긋나지 않는다 |
| `src/dataset.py` | 모델에 넣을 샘플을 만든다. 시각 t마다 "과거 L칸의 값·시각·일정", "앞으로 60분의 예정 인원", 정답(지금 값에서 얼마나 바뀔지)을 만든다 |
| `src/models.py` | 모델 구조. GRU·LSTM(순환망), TCN(합성곱, 과거 5시간 15분을 봄), 오토인코더(1시간 창을 다시 그려 보는 모델) |

**과제별 코드 (`src/`)**

| 파일 | 과제 | 처리 순서 |
|---|---|---|
| `diagnose.py` | 2 | 빈칸 비율·지운 값 세기 → 평일 시간대별 평균 그래프 → 일정이 바뀐 뒤 CO₂가 몇 분 만에 반응하는지 재기 → 휴강·노쇼처럼 일정과 실제가 어긋난 날 찾기 |
| `baselines.py` | 2 | 평가 지점 고정(이후 모든 모델이 같은 지점 사용) → 기준선 3가지로 5·15·30·60분 뒤 오차 계산 |
| `train_forecast.py` | 3 | 모델·과거 길이마다 학습 → 검증 기간 오차로 고르기 → 시험 기간은 마지막에 한 번만 평가. 일정 제외, 한 공간 빼고 학습하기 실험도 한다 |
| `anomaly.py` | 4 | 오토인코더를 정상 데이터로 학습 → 규칙(급변·값 고정·영점) → 최근 7일 정상 범위 → 예측 오차 → 검증 기간 헛경보로 기준 정하기 → 경보를 30분 단위 사건으로 묶어 고장 17건과 비교 |
| `state.py` | 5 | 사용 여부: 일정으로 정답을 만들고 센서값만으로 분류 모델 학습 → 관찰 시간대로 평가. 환기 경보: "30분 안에 1,000ppm 초과"를 양성으로 두고 학습, 기준은 검증 기간에서 정하기 |
| `pretrained.py` | 6 | Chronos에 과거 CO₂를 넣어 60분 예측(학습 없음) → 과거 길이별 오차·예측 구간 적중률 → 추론 시간·메모리 측정 |
| `optimize.py` | 7 | 모델을 ONNX로 내보내고 TensorRT 엔진으로 변환 → 네 가지 실행 방식으로 500회씩 실행해 지연 측정 → 변환 전후 결과 차이 → 측정 중 전력 기록 |
| `trt_mixed.py` | 7 | GRU·LSTM을 순환층만 FP32로 두고 다시 변환해 차이를 1ppm 아래로 맞춤 |
| `service.py` | 8 | 매분: InfluxDB에서 최근 값 읽기 → 학습과 같은 전처리 → 예측·이상·사용 여부·환기 경보 계산 → 경보는 30분에 한 번만 알림 → MQTT 발행·API·InfluxDB 기록. 한 번 실패해도 다음 주기에 다시 계산 |
| `run_*.sh` | 6·7·8 | 여러 모델을 차례로 돌리거나(`run_pretrained.sh`, `run_optimize.sh`), 서비스가 죽으면 다시 띄우는(`run_service.sh`) 실행용 스크립트 |
| `b*.py`, `b*.sh` | 심화 | 과제별 심화 실험(번호가 과제 번호) |

## 자주 나오는 질문

- **왜 전처리를 한 파일에 모았나**: 학습과 서비스의 전처리가 조금만 달라도 모델이 오류 없이 조용히 틀린다. 그래서 `prep.py` 하나를 둘 다 쓴다.
- **왜 변화량을 맞히게 했나**: CO₂는 몇 분 사이에 거의 그대로라, "지금 값에서 얼마나 바뀔지"만 배우면 되기 때문이다.
- **왜 평가 지점을 고정했나**: 기준선과 모든 모델을 똑같은 시각에서 비교해야 공정하기 때문이다(`results/synthetic/eval_points.csv.gz`).
